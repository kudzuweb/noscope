noscope architecture

How an incident moves through the runtime, what each part receives and returns, and where humans and models sit in the loop. Companion to DESIGN.md; vocabulary is ICS's throughout.

2. One cycle, in order noscope incident step

Every step runs exactly this and stops. run repeats it until the incident leaves open.

1
Observe: render the incident file into the planner's input
Carries, in a stable order so the prompt prefix caches: objective, constraints, priorities, budget remaining, grants given, unanswered questions · verified claims · asserted claims with provenance · the unit tree with each unit's purpose and status · tasks completed since last cycle, each as a summary against its contract plus evidence pointers · tasks that came back insufficient with what they needed · open tasks · the capability registry, and every model each provider serves with its cost · the validator's rules.
↓
2
Plan: one headless provider call returns an action plan
Claude Code, --model claude-opus-5, no tools, --json-schema, the five isolation flags. Returns ActionPlan: createUnits (purpose, parent) · closeUnits (id, reason) · createTasks (unit, capability, objective, inputs, completion criteria, evidence required, instructions, provider, model) · cancelTasks · claimsToVerify · questionsForHuman · grantRequests · capabilityRequests · applySops · incidentStatus · rationale. The planner never runs a tool or writes to the store.
↓
3
Validate: every rule passes or the whole plan is rejected
Capabilities exist · units and parents exist · no cycles · no duplicate task · inputs parse against the capability's input schema · span of control ≤ 7 direct children, target 5 · effect policy (v0: read_only only; later: a grant on this incident) · budget fits · dependencies resolve · closing is clean · status is earned · model known (provider and model pair the provider serves). A rejection writes plan.rejected with the failing rule and is fed back as input next cycle.
↓
4
Apply: the tree changes shape
Units created and closed, tasks created and cancelled, all in one transaction with their events: unit.created, unit.closed, task.created, task.cancelled, plan.applied. If the plan carried questions for a human, the incident goes to blocked and stops here (see §5).
↓
5
Dispatch: run every ready task
Ready means every depends_on task is completed. v0 runs them one after another (parallel is the after-v0 lever). Each run writes task.started, then the result with task.completed, task.failed or task.insufficient, plus task.usage from the provider's usage fields, and the time bound is enforced.
↓
6
Verify: results become claims
A deterministic capability's result → verified claims, provenance = capability + inputs. A session's result → asserted claims, provenance = session id. An insufficient result → no claims, an event carrying what was needed. A claimsToVerify entry schedules a deterministic task whose match promotes the asserted claim (§4).
↓
7
Record and stop
The incident file now holds the new tree, claims and events. step prints the plan, the validator's verdict, what ran and what changed. satisfied requires every open task completed or cancelled and at least one verified claim.
↺next step reads the updated incident file

3. What a session receives and returns

Into the session

  • System prompt = the fixed preamble + the capability's own role text. The preamble orients the session: this is an agentic runtime modeled on the Incident Command System; an incident is any objective Mauria asks to have pursued; a temporary organization of units is built around it and torn down when done; the planner drafts an action plan each cycle, a validator approves it, tasks run through capabilities. Then the term mapping, one line each: incident, unit, task, capability, equipment, claim and its statuses, action plan, planner, grant, budget, SOP. Then the session's place: a resource assigned to one task in one unit; report only against the task's contract; findings are asserted until verified; it cannot change the organization; when it lacks something it answers insufficient and names the kind: a retrievable fact, permission, missing means, or a human's knowledge.
  • User message = the task: objective, inputs, expected output, completion criteria, evidence required, instructions, and one line saying what the owning unit is trying to establish.
  • Equipment = exactly what the capability declares: built-in tools via --tools, Bash under --allowedTools Bash(cmd *), and after v0 the runtime's MCP server and any external MCP servers via --mcp-config --strict-mcp-config. --tools "" leaves only MCP equipment.
  • Model named by the task, any the provider serves. Isolation: --setting-sources "", --disable-slash-commands, --exclude-dynamic-system-prompt-sections, --no-session-persistence; Mauria's CLAUDE.md, skills, hooks and permissions never load (≈3k tokens of context, 2.5k with no built-ins).
  • Output schema via --json-schema.

Out of the session

  • outcome: answered | insufficient.
  • If answered: claims (subject, predicate, object, confidence, evidence pointers), all entered as asserted.
  • If insufficient: needed, the evidence or access it lacked, and no claims. The planner sees this next cycle and creates the task that supplies it, or asks Mauria.
  • Usage: tokens and time, recorded as task.usage against the budget.
  • The provider's session id, as provenance on every claim.

4. A claim's life

a
Asserted
A session says "the save path calls normalize() before writing". Entered as asserted with the session id. The planner sees it under asserted claims and may list it in claimsToVerify.
↓planner requests verification
b
A deterministic task checks it
The validator admits a task to grep or read with inputs derived from the claim; the equipment runs in-process, milliseconds, no model.
↓
c
Verified, or rejected
A match promotes the claim to verified (claim.verified); a mismatch marks it rejected (claim.rejected). Only verified claims can satisfy an incident. Nothing a model said becomes true without this step.

5. Where the loop waits on Mauria

The planner has four channels for what it lacks, and only the last three wait on her: a fact a registered capability can retrieve is a task, resolved by the runtime next cycle.

The means it does not have

  • Planner puts a capabilityRequest in the plan: what it would need and why, such as equipment that reads a GitHub issue; the incident goes blocked; capability.requested.
  • noscope incident show prints it. Mauria registers the capability or equipment, and the next step plans with it. After v0, when the missing thing is an external MCP server, the planner can declare it itself.
  • This is also the runtime telling her what to build next.

A question only she can answer

  • Planner puts it in questionsForHuman; the incident goes blocked; question.asked.
  • noscope incident show prints it; when noscope runs inside a Claude Code session the runtime can send it as an agent message.
  • noscope incident answer <id> "…" records question.answered and returns the incident to open; the answer enters the planner's input next cycle.

A grant for a capability that writes after v0

  • Planner puts a grantRequest (capability, effect, reason) in the plan; the validator holds any task needing it; grant.requested.
  • noscope incident grant <id> <capability> gives a per-incident grant covering every task on it; --per-task makes each task ask again; noscope grant standing whitelists everywhere. The three stack.
  • v0 registers only read_only capabilities, so this path is never taken yet.

Budgets she sets

  • Tokens, time or both, on the incident or a task; unlimited by default in v0.
  • The planner sees what remains and the cost facts stored on each capability and piece of equipment; the validator rejects a task that does not fit; the dispatcher enforces the time bound and records usage.

Events tell why the topology changed: unit.created, claim.verified, unit.closed, each with the plan's rationale. Span of control keeps any unit at ≤ 7 direct children, so twelve tasks force the planner to invent branches. The unit names above are illustrative; the planner writes its own.

7. Equipment and capabilities

Equipment (primitive, never assigned)

  • Function: read_file, stat_path, grep_files, list_directory, git_status, git_log, git_diff, run_readonly. A deterministic capability calls it in-process, milliseconds. A session reaches it only through the runtime's own MCP equipment server after v0: one process per session, advertising exactly the capability's declared function equipment, every call logged as an event.
  • Provider built-in tool: Read, Grep, Glob, Bash under an allowlist; only inside a session, passed with --tools.
  • External MCP server after v0: Craft, GitHub, a browser, declared by name and launch command, passed to the session beside the runtime's own server.
  • Each declares cost facts: rate limit, typical tokens and seconds, money per call.

Capability (the assignable thing)

  • name, description, equipment, input/output zod schemas, effect (read_only | writes_local | writes_external), produces (verified_claims | asserted_claims), cost, paths (the input fields resolved against the incident cwd), and by kind either a run function or a session with its system prompt.
  • v0: check_path, read, grep, git_history (deterministic) · investigate, interpret (session-backed, model per task).
  • A capability may include other capabilities.

SOP after v0

  • A saved unit configuration: purpose, the tasks it opens with their capabilities, instructions and equipment, the angles the planner may choose among, completion criteria.
  • Added by noscope incident sop <id> code-review or by the planner's applySops; the whole unit lands in one action plan.

8. Speed, measured on this machine

Headless startup ≈ 3 s per session · Haiku session with one Bash call 4.4 s API · Opus planner call 14.2 s API · deterministic capability: milliseconds. One cycle ≈ planner + tasks in sequence; five cycles with two sessions each ≈ 3–4 minutes. After v0, parallel dispatch turns the sum into a maximum.
