noscope architecture

How an incident moves through the runtime, what each part receives and returns, and where humans and models sit in the loop. Companion to DESIGN.md; vocabulary is ICS's throughout.

2. One cycle, in order noscope incident step

Every step runs exactly these eight steps, one operational period, and stops. run repeats it until the incident leaves open. At most two planner calls and two IC reads per cycle, plus one handoff call before the command turn or a review when the IC's last call reached the context threshold; the IC is never consulted per task.

1
Brief the IC: the change report, then the incident file
The change report since the IC last acted: every picture.discrepancy first, every unit.reported since its last accepted command turn (the reports its verdicts must answer, R4-2) headed by the unit id and the report's event id (outcome, picture changed, what changed on which claims, why and suggestion for not_met) with the work behind it for the IC to judge the account against (round 4, R4-1: the unit's tasks since its previous report with capability, objective, how each ended and what it came to, the claims each produced with basis and confidence, the unit's tool calls by tool with counts; each task's block clipped at NOSCOPE_REPORT_WORK_CHARS characters, 1,500 by default, the task id pointing to the full record), then every task under command that ended, one block each in the same form, a deterministic result's text whole under the cap since no leader reads the root's results (R4-6), the resource requests each waiting unit still waits on, with the text an answer names one by, questions answered and capabilities provided, the rules its last turn failed, the spend since then. On the IC's first turn after a transfer of command, the incident briefing next, and the ask opens with the instruction to evaluate it. Then the incident file rendered as the planner reads it (step 3), in a stable order so the prompt prefix caches: objective, constraints, priorities, the current period, budget remaining, grants given, unanswered questions · claims, each with its status, basis and provenance (a capability's summarized predicate, grep's matches, in full only in their first cycle or when the situation keeps them, then one line per task) · the unit tree with each unit's objective, status, leader model, last report outcome and the IC's last verdict on it · tasks completed since last cycle, each against its contract, a session's findings in full and a deterministic result clipped · tasks that came back insufficient with what they needed · unit reports since last cycle · open tasks · the capability registry, and every model each provider serves with its cost · the validator's rules · the IC's situation from its last accepted command turn, with the ids of the reassignments still open under it (R4-5).
↓
2
Command turn: the IC sets the operational period
The IC's session resumed with the briefing under CommandTurn: periodObjectives · priorities, restated or revised · reportVerdicts, one per unit whose report the change report lists (R4-2): the unit and the event id of its last report in the window (an earlier one the same pass is marked as answered through it), accepted, revise or reassign, instructions (required for revise and reassign, empty for accepted) and a why · situation (R4-5): what changed, the hypothesis, the observed claims it rests on, every inferred link settled by a task (an open task's id, or the ref the plan is to give it) or deferred with a why, the claims to keep in view, a reassignment written into the slice it concerns · closeUnits, for units that did not report · dropReassignments, open reassignments the IC drops rather than have a plan take (R4-4) · answers to units' resource requests it can answer itself · questionsForHuman · capabilityRequests · grantRequests · incidentStatus · rationale · discrepancy. Held to Units exist, Closing is clean and Status is earned, the verdicts' closes folded in, and to Answers match, Reports answered (every reporting unit answered exactly once, on its last report, and none outside the window), Drops match (each drop names an open reassignment) and Situation grounded (every claim the situation names exists, and every proven one was observed; R4-5). A failing rule writes command.rejected and ends the cycle without advancing the period; the unanswered reports are listed again for the retry. An IC call that gets no usable answer writes command.failed with its usage. Before the turn, when the IC's last call reached NOSCOPE_IC_HANDOFF_TOKENS, the outgoing session writes its HandoffDocument and is released (leader.released with the document and the call's usage); the turn then runs on a fresh session whose briefing opens with the transfer, the document and the instruction to evaluate it, and command.transferred is written with the successor's leader.started. Applied like a plan: command.turned with the period as its mutation, one report.reviewed per verdict (actor ic), one unit.reassigned per reassign verdict (R4-4: the reassignment's id, the unit and its objective, the instructions, the claims by id, dropped on a drop:), then closes (by closeUnits and by an accepted or reassigned verdict, through unit.closed with the verdict as the reason; a revised unit stays active), a reassigned unit's open tasks cancelled, questions and requests with their events, the status. A status other than continue ends the cycle here: blocked on what the IC raised, or satisfied or failed.
↓
3
Plan: one stateless headless provider call returns a draft
Claude Code, --model claude-opus-5, no tools, --json-schema, the four isolation flags, the period's objectives and priorities in section 1. Returns ActionPlan: createUnits (objective, parent, leader provider and model, equipment, Bash allowlist, and takes naming an open reassignment, R4-4) · closeUnits (id, reason) · createTasks (ref, unit, capability, objective, inputs, completion criteria, evidence required, dependsOn as task ids or refs in this plan, evidenceFrom as claims by id and tasks by id or ref, instructions, provider, model) · cancelTasks · questionsForHuman · grantRequests · capabilityRequests · applySops · incidentStatus · rationale, saying how the plan works the IC's situation · discrepancy, only when the file describes a different problem from the one planned. The plan is the tactics, suggested to the IC (R4-5); the validator holds it to every inferred link the IC's situation names (Inferred links are worked). The planner never runs a tool or writes to the store; plan.proposed per draft.
↓
4
Review: the IC reads the draft once
The IC's session resumed with the draft under ReviewTurn: approve applies it as drafted · correct (when the planner must re-plan, since it holds the file's refs and tasks) sends corrections to the planner, which redrafts once with its draft and the corrections appended after the file, and the IC reads the redraft under FinalReviewTurn, approve or amend only · amend when the change is small and exact · amend returns the whole plan as the IC wants it applied. Each read writes plan.reviewed with the verdict and the call's usage. The same handoff runs before a review when the command turn's context reached the threshold: the fresh session is briefed with the transfer, the document and the file before the draft, and evaluates the document in the review's optional briefingEvaluation.
↓
5
Validate: every rule passes or the whole plan is rejected
Capabilities exist · units and parents exist · no cycles · no duplicate task · inputs parse against the capability's input schema · span of control ≤ 7 direct children, target 5 · effect policy (v0: read_only only, and a new unit's leader gets only known equipment and read-only Bash; later: a grant on this incident) · budget fits · dependencies resolve · closing is clean (and a unit whose leader has a session closes only after it has reported) · reassignments taken (every open reassignment named in exactly one new unit's takes, R4-4) · status is earned · model known (provider and model pair the provider serves, for tasks and for new units' leaders). A task's strike team is held to three of these and nothing else: its model (model known), its tools read-only built-ins (effect policy), its count inside the task's token bound (budget fits). A rejection writes one plan.rejected per failing rule, with its reason, and is fed back as input next cycle. A plan that passes may still be warned on (session work under the root: it runs in its own session with no leader to judge it), written as plan.warned, printed by step and shown to the planner in section 9; the plan is applied as it stands (R4-6). The plan checked is the one to apply: the draft, the redraft, or the IC's amended plan.
↓
6
Apply: the tree changes shape
Units created and closed, tasks created and cancelled, all in one transaction with their events: unit.created (with reassignment.taken for a unit that takes one, R4-4), unit.closed, task.created (with strike_team.defined for a task that declares a team), task.cancelled, plan.applied carrying the IC's verdict, its corrections, and the diff between the planner's first draft and the applied plan (each array as a set, the other fields named when changed). If the plan carried questions for a human, the incident goes to blocked and stops here (see §5).
↓
7
Dispatch: run the units under their leaders, to their reports or a change of picture
Ready means every depends_on task is completed. Units with no dependency between them run at once, up to NOSCOPE_PARALLEL passes; related units run one at a time in tree order. In a unit, every runnable task starts at once (in process or in its own session; tasks inside the leader's session one at a time), and each ending is put to the leader on a turn of its own (the root excepted: its tasks run with no turn between, none inside the IC, and its pass ends when they have run; the IC judges them from its change report, R4-6): continue starts what the ending made runnable, or report, which ends the unit's pass while its tasks in flight land; a report that changed the picture ends the whole pass, nothing new starts, and every run in flight lands first. A task that came back insufficient reaches the leader with what it needed: a retrievable fact the leader assigns a task for (assignTasks, validated as a plan's tasks are plus the leader's own rules, applied as plan.applied by the actor leader, run in the same pass); the other three kinds it sends up as resourceRequests on its report, which is then picture-changing and puts the unit in waiting (unit.waiting) until the IC or Mauria answers (unit.resumed), while the other units keep running. A unit whose report the IC sent back (revise, R4-2) opens its next pass with the revision brief as its first turn, before any task (R4-3): the instructions and why, the report reviewed and the period objectives, on its resumed session or a fresh oriented one when it has none; the leader assigns what is missing and continues, or reports at once; unit.revised is written with that turn, and the report answering it carries revision, numbered from the verdicts. A unit that took a reassignment (R4-4) reads it in its orientation on its first call: the closed unit and its objective, the IC's instructions and why, and the closed unit's claims by id. Each task's run writes task.started, then the result with task.completed, task.failed or task.insufficient, plus task.usage from the provider's usage fields and one tool.called per tool call and subagent.ran per subagent, and the time bound is enforced; each turn writes unit.continued or unit.reported with its own usage, the first records leader.started, and a discrepancy writes picture.discrepancy. A task that declares a strike team (by the plan, or by its leader's requestStrikeTeam on the turn before it, checked and written as strike_team.defined or refused as strike_team.rejected) has its kinds defined for the call that runs it, with the Agent tool; each member the session sends is a subagent.ran under the task.
↓
7
Verify, inside dispatch: results become claims
A deterministic capability's result → verified claims, provenance = capability + inputs. A session's result → asserted claims, provenance = session id. An insufficient result → no claims, an event carrying what was needed. The status never changes after entry; it names the source, and the basis (observed or inferred) is what the validator reads (§4).
↓
8
Stop
The incident file now holds the period, the new tree, claims and events. step prints the IC's turn, the draft, the IC's verdict, the validator's verdict, what ran, each unit's report and what changed. satisfied, from the IC or the planner, requires every open task completed or cancelled and at least one observed claim, from equipment or a session. The next step's change report opens with whatever changed the picture.
↺next step reads the updated incident file

3. What a session receives and returns

Into the session

  • System prompt = the fixed preamble + the seat's place + the role text (a capability's for a task session, LEADER_ROLE for a unit leader, IC_ROLE for the IC, INITIAL_IC_ROLE for the initial IC). The preamble orients the session: this is an agentic runtime modeled on the Incident Command System; an incident is any objective Mauria asks to have pursued; a temporary organization of units is built around it and torn down when done; the IC sets objectives and priorities, the planner drafts an action plan each operational period, the IC approves it, a validator checks it, the units run their tasks under their leaders and report. Then the term mapping, one line each: incident, Incident Commander, initial IC, unit, unit leader, task, capability, equipment, subagent, strike team, task force, claim and its statuses and bases, situation report, action plan, operational period, planner, transfer of command, grant, budget, SOP; the confidence scale; the four kinds of lack. Then the seat's place: a task session is a resource assigned to one task in one unit under its leader, reports only against the task's contract, cannot change the organization, and answers insufficient naming the kind of lack; a leader owns its unit's objective, runs or receives its tasks, and continues or reports; the IC leads the root unit, command, sets each period's objectives and priorities, reviews the draft and reads the reports; the initial IC sizes the incident up, briefs, hands over and decides nothing that lasts.
  • User message = the brief: the incident objective, the period's objectives and priorities, the IC's situation (R4-5), the hierarchy around the unit (its leader, who it reports to, what is below it), the task: objective, inputs, expected output, completion criteria, evidence required, instructions, the strike team it declares (each kind, its shape and why, how to send a member and cite its agentId), and one line saying what the owning unit is trying to establish. A leader's first call opens with its orientation; each later call resumes the session with a task's brief or a turn, which names the task that runs next and how to ask for a team on it.
  • Equipment = exactly what the capability declares: built-in tools via --tools, Bash under --allowedTools Bash(cmd *), and, per capability, external equipment via --mcp-config --strict-mcp-config with its tools allowlisted (round 2); the runtime's own MCP server stays after v0, reached the same way, --mcp-config --strict-mcp-config. --tools "" leaves only MCP equipment. A declared strike team adds --agents defining each kind (name, why as its description, prompt, model, tools) for that call alone, and Agent to the tools and the allowlist; no kind exists otherwise.
  • Model named by the task, any the provider serves. Isolation: --setting-sources "", --disable-slash-commands, --exclude-dynamic-system-prompt-sections, --strict-mcp-config; Mauria's CLAUDE.md, skills, hooks, permissions and claude.ai connectors never load (≈3k tokens of context, 2.5k with no built-ins). The transcript is kept, under Claude Code's project directory for the session's working directory, keyed by the session id the log records.
  • Output schema via --json-schema.

Out of the session

  • outcome: answered | insufficient.
  • If answered: claims (subject, predicate, object, basis observed or inferred, confidence, evidence pointers), all entered as asserted.
  • If insufficient: needed, the evidence or access it lacked, each with its kind, and no claims. The unit's leader sees this on its next turn: it assigns a task for a retrievable fact itself, and sends permission, missing means or human knowledge up as resource requests on its report.
  • Usage: input tokens with their uncached, cache-write and cache-read split, output tokens, time, and the provider's cost at list price, recorded as task.usage against the budget.
  • Activity: every tool call the session makes is a tool.called event under its task (tool, input, result clipped at 4k characters with the transcript as the full record, error flag, duration), and every subagent it spawns is a subagent.ran event read from the subagent's transcript (type, model, the Agent call that spawned it, its own usage as a breakdown never added to the task's, and its own calls as nested tool.called events).
  • The provider's session id, as provenance on every claim; for a task run inside its leader's session, the leader's.

4. A claim's life

A claim's status is a label for its source and never changes: verified means deterministic equipment produced it, asserted means a session did. What the planner and validator read is the basis.

a
Entered, with a status and a basis
A session says "the save path calls normalize() before writing" and marks it observed (seen in the code) or inferred (reasoned from what it saw). Entered as asserted with the session id. A grep or read result enters as verified, basis observed, with the inputs that ran.
↓the planner reads section 2
b
Placed in the IC's situation
An observed claim, from either source, may go in proven; an inferred one goes in inferred with what settles it: a task, a reproduce task whose observations enter as observed claims, or deferred with a why (R4-5).
↓
c
Gates on basis, never on status
The validator refuses a proven entry whose basis is inferred, and refuses satisfied with no observed claim. Round 3 removed promotion: in both live runs no asserted claim was ever promoted, and the observations that settled run 002 were session claims.

5. Where the loop waits on Mauria

Every seat has four channels for what it lacks, and only the last three wait on her: a fact a registered capability can retrieve is a task, resolved by the runtime next cycle when the IC or the planner lacks it and by the unit's leader in the same pass when a task does. A lack is resolved by the nearest seat that can: the IC raises its own in its command turn, the planner in its plan, and a unit leader sends the three it cannot resolve up as resource requests on its report, which the IC answers when it can and Mauria otherwise.

The means it does not have

  • Planner puts a capabilityRequest in the plan: what it would need and why, such as equipment that reads a GitHub issue; the incident goes blocked; capability.requested.
  • noscope incident show prints it. Mauria registers the capability or equipment, and the next step plans with it. After v0, when the missing thing is an external MCP server, the planner can declare it itself.
  • noscope incident provide <id> "…" records capability.answered with what was provided, or why not, and returns the incident to open once nothing else waits; the answer enters the planner's input next cycle.
  • A unit leader raises the same thing as a missing_means resource request on its report: the request names the unit, the unit goes waiting and the incident stays where it was; the IC's command turn or incident provide answers it, and the unit returns to active once nothing of its is open, the leader reading the answer before its next task.
  • This is also the runtime telling her what to build next.

A question only she can answer

  • The IC or the planner puts it in questionsForHuman; the incident goes blocked; question.asked. A discrepancy the IC cannot reconcile from the file arrives this way.
  • noscope incident show prints it; when noscope runs inside a Claude Code session the runtime can send it as an agent message.
  • noscope incident answer <id> "…" records question.answered and returns the incident to open; the answer opens the IC's next change report and enters the planner's input next cycle.
  • A unit leader asks the same way with a human_knowledge resource request on its report: the question names the unit, the unit goes waiting, the incident stays open, and the IC's command turn or incident answer returns the unit to active with the answer in its leader's next turn.

A grant for a capability that writes after v0

  • Planner puts a grantRequest (capability, effect, reason) in the plan; the validator holds any task needing it; grant.requested.
  • noscope incident grant <id> <capability> gives a per-incident grant covering every task on it; --per-task makes each task ask again; noscope grant standing whitelists everywhere. The three stack.
  • A unit leader's permission resource request is recorded as grant.requested naming the unit, and holds the unit as the planner's holds the incident.
  • v0 registers only read_only capabilities, so this path is never taken yet.

Budgets she sets

  • Tokens, time or both, on the incident or a task; unlimited by default in v0.
  • The planner sees what remains and the cost facts stored on each capability and piece of equipment; the validator rejects a task that does not fit; the dispatcher enforces the time bound and records usage.

7. Equipment and capabilities

Equipment (primitive, never assigned)

  • Function: read_file, stat_path, grep_files, list_directory, git_status, git_log, git_diff, run_readonly. A deterministic capability calls it in-process, milliseconds. A session reaches it only through the runtime's own MCP equipment server after v0: one process per session, advertising exactly the capability's declared function equipment, every call logged as an event.
  • Provider built-in tool: Read, Grep, Glob, Bash under an allowlist; only inside a session, passed with --tools.
  • External: an MCP server declared by name and launch command (playwright_browser, headless), or a provider integration named as equipment (claude_in_chrome, interactive-only); passed to the session with --mcp-config and --strict-mcp-config, its tools allowlisted as mcp__<server>. The runtime's own equipment server stays after v0.
  • Each declares cost facts: rate limit, typical tokens and seconds, money per call.

Capability (the assignable thing)

  • name, description, equipment, input/output zod schemas, effect (read_only | writes_local | writes_external), produces (verified_claims | asserted_claims), cost, paths (the input fields resolved against the incident cwd), summarize (the predicate whose claims the planner sees in full only in their first cycle), and by kind either a run function or a session with its system prompt.
  • v0: check_path, read, grep, git_history (deterministic) · investigate, interpret (session-backed, model per task).
  • A capability may include other capabilities.

SOP after v0

  • A saved unit configuration: purpose, the tasks it opens with their capabilities, instructions and equipment, the angles the planner may choose among, completion criteria.
  • Added by noscope incident sop <id> code-review or by the planner's applySops; the whole unit lands in one action plan.

8. Speed, measured on this machine

Headless startup ≈ 3 s per session · Haiku session with one Bash call 4.4 s API · Opus planner call 14.2 s API · deterministic capability: milliseconds. One cycle ≈ the IC's two resumed calls + planner (twice on a correction) + the longest chain of dependent tasks, since unrelated units and independent tasks run at once (R4-9); incident review prints each cycle's wall time beside the sum of its tasks' seconds and their ratio.
